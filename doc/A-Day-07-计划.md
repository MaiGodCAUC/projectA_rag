# A-Day 7：RAGAS 评估体系

## 核心目标

建立 RAG 量化评估体系，用 RAGAS 框架的 4 项指标评估系统质量，
输出评估报告（含雷达图 + Bad Case 分析），形成「评估 → 优化 → 再评估」的闭环。

## 学习内容

### 1. RAGAS 四大指标

| 指标 | 英文 | 评估对象 | 通俗理解 | 计算方式 |
|------|------|---------|---------|---------|
| 忠实度 | Faithfulness | 生成回答 | 回答是否100%基于检索到的文档？有没有编造？ | 从回答中提取断言 → 逐一验证是否在上下文中 |
| 回答相关性 | Answer Relevancy | 生成回答 | 回答是否紧扣用户问题？有没有跑题？ | 用LLM生成反向问题 → 算余弦相似度 |
| 上下文精确度 | Context Precision | 检索结果 | 检索到的文档中，相关文档排在第几位？ | 检索结果中相关文档的平均排名 |
| 上下文召回率 | Context Recall | 检索结果 | 标注答案中的内容，检索结果覆盖了多少？ | 标注答案中的句子被检索结果覆盖的比例 |

### 2. 评估数据集构建

- **手工标注 30 条 QA 对**：覆盖 7 类文档，每类 4~5 条
- **LLM 辅助生成**：从文档中自动提取 QA 对扩充评估集
- **标注字段**：question / answer / context（期望命中的文档+条款）

### 3. RAGAS 工作原理

```
评估数据集 (QA pairs)
        │
        ▼
┌───────────────────┐
│ 你的 RAG 系统      │  ← 对每条 question 走完整流程
│ 检索 → 生成 → 回答 │
└────────┬──────────┘
         │
         ▼
┌───────────────────┐
│ RAGAS 评估器       │  ← 对比「系统回答」和「标注回答」
│ Faithfulness      │
│ Answer Relevancy  │
│ Context Precision │
│ Context Recall    │
└────────┬──────────┘
         │
         ▼
    评估报告（雷达图 + 指标表）
```

### 4. RAGAS 到底评估的是什么？—— RAG 管线的两层拆解

RAG 系统能拆成**两个独立环节**，RAGAS 的 4 项指标精准地各自盯住其中一个：

```
用户: "金卡会员能带人进休息室吗？"
        │
        ▼
┌─────────────────────────────────────────────────────────┐
│  ① 检索层 (Retrieval)                                    │
│     ┌──────────┐    ┌──────────┐                        │
│     │ 向量检索   │ +  │ BM25检索  │ → 返回 Top-5 文档片段  │
│     └──────────┘    └──────────┘                        │
│                                                         │
│     RAGAS 盯这里的指标:                                   │
│     · Context Precision  —— 返回的5条里有几条真的相关？   │
│     · Context Recall     —— 标准答案里的要点，检索覆盖了吗？│
└─────────────────────────┬───────────────────────────────┘
                          │ Top-5 文档片段
                          ▼
┌─────────────────────────────────────────────────────────┐
│  ② 生成层 (Generation)                                   │
│     Prompt(检索结果 + 用户问题) → LLM → 回答文本          │
│                                                         │
│     RAGAS 盯这里的指标:                                   │
│     · Faithfulness      —— 回答有没有编造文档里没有的内容？│
│     · Answer Relevancy  —— 回答有没有跑题？              │
└─────────────────────────────────────────────────────────┘
```

**面试话术**："RAGAS 的设计精髓在于把 RAG 的检索层和生成层分开评估。Context Precision 和 Recall 排查检索问题，Faithfulness 和 Answer Relevancy 排查生成问题。当 Faithfulness 低但 Context Precision 高，说明检索没问题但 LLM 在瞎编——这时候该优化 Prompt 或换模型，而不是去调 BM25 参数。"

### 5. 市面上还有哪些评估方法？

#### 5.1 人工评估 (Human Evaluation)

| 维度 | 说明 |
|------|------|
| 做法 | 找 2-3 个人，对每条回答打分（1-5分） |
| 优点 | 最准确——人最懂"好不好" |
| 缺点 | **不可规模化**——30 条还能人工，300 条就崩溃了；**不可复现**——同一个人上午和下午打分可能不同 |
| 适用 | 上线前的最终验收，或和自动化评估做交叉验证 |

#### 5.2 传统 NLP 指标 (BLEU / ROUGE / METEOR)

| 指标 | 原理 | RAG 场景的问题 |
|------|------|---------------|
| BLEU | 比较生成文本和参考答案的 n-gram 重叠率 | LLM 回答和标注答案**用词可能完全不同但都正确**，如"每公斤100元" vs "100元/kg"→ BLEU 判错 |
| ROUGE | 比较生成文本和参考答案的召回率 | 同上，只看字面重叠不看语义 |
| METEOR | BLEU 的改进版，加入同义词匹配 | 稍微好点，但仍然不理解语义 |

**根本问题**：传统指标是"比字面"，RAG 需要"比语义"。这类指标现在基本不用于 RAG 评估。

#### 5.3 LLM-as-a-Judge（直接用 GPT-4 打分）

| 维度 | 说明 |
|------|------|
| 做法 | Prompt GPT-4："以下是用户问题、参考文档和系统回答，请从 1-5 打分并说明理由" |
| 优点 | 比传统 NLP 指标好很多——LLM 理解语义 |
| 缺点 | ① 没有标准化的评分维度和 Prompt ② 单次打分容易受 LLM 自身偏差影响（如偏好长回答、偏好肯定语气）③ 不可复现——同样的输入打两次可能不同 |
| 代表 | 很多团队自己写 Prompt，缺乏统一标准 |

#### 5.4 其他评估框架

| 框架 | 定位 | 和 RAGAS 的差异 |
|------|------|----------------|
| **RAGAS** | 专注 RAG 的理论化评估 | 基于论文的标准化指标，有明确的数学定义和验证实验 |
| **DeepEval** | 通用 LLM 评估框架 | 指标更多但更泛化，RAG 专用性不如 RAGAS |
| **TruLens** | 可观测性 + 评估一体 | 侧重在线监控，评估方法论比 RAGAS 弱 |
| **Arize Phoenix** | 可观测性平台 | 强在 Trace 可视化，评估是副业 |

### 6. RAGAS 科学在哪里？

RAGAS 不是凭感觉设计的，它有一篇学术论文支撑：

> **论文**: "RAGAS: Automated Evaluation of Retrieval Augmented Generation" (2023, Shahul Es 等)

#### 6.1 每项指标都有严格的数学定义

**Faithfulness（忠实度）** 的计算不是"让 LLM 打个分"，而是：

```
步骤 1: 用 LLM 从回答中提取所有"原子断言"(atomic claims)
        例: 回答="按每公斤100元赔偿，7日内提出索赔"
               → 提取: [claim1: 赔偿标准是每公斤100元,
                        claim2: 索赔时限是7日内]

步骤 2: 对每条原子断言，用 NLI(自然语言推理)判断：
        能否在检索到的文档中找到支撑？
        → claim1: 文档中找到了"100元/kg" → ✅ 有支撑
        → claim2: 文档中找到了"7日内书面提出" → ✅ 有支撑

步骤 3: Faithfulness = 有支撑的断言数 / 总断言数
         = 2/2 = 1.0
```

**为什么这比"让 LLM 打个分"更科学？**
- 分解为原子断言 → 粒度细，不会因为回答"大部分对"就给高分
- NLI 判断 → 每个断言都有明确的"找到/没找到"依据，不是模糊打分
- 可审计 → 你可以人工抽查"这个断言真的在文档里吗？"

#### 6.2 有黄金标准验证实验

RAGAS 论文用 **WikiEval** 数据集做了验证——同时收集了人工评分和 RAGAS 自动评分，计算两者的相关性：

| 指标 | 与人工评分的 Spearman 相关系数 | 解读 |
|------|-------------------------------|------|
| Faithfulness | 0.80+ | 和人的判断高度一致 |
| Answer Relevancy | 0.75+ | 和人的判断比较一致 |
| Context Precision | 0.70+ | 基本一致，但检索质量的评估相对更难 |
| Context Recall | 0.65+ | 略低但可接受——recall 本身定义就有主观性 |

**这意味着什么？** RAGAS 的自动评分和真人打分有 70-80% 的一致性——它不是替代人工评估，而是在"人工评 30 条也不准"和"自动评 3000 条全覆盖"之间取了最优解。

#### 6.3 为什么选 RAGAS 而不是自己写评估 Prompt？

| 自己写 Prompt 评估 | 用 RAGAS |
|-------------------|---------|
| 你需要自己定义"好回答"的标准 | 有论文定义好的标准，面试时能引论文 |
| 遇到"跑题"vs"不忠实"不好区分 | 4 项指标各自盯一个维度，不混淆 |
| 只能给一个总分 | 能告诉你"检索差但生成好"→ 精准定位瓶颈 |
| 面试官会质疑你的方法论 | 面试官自己可能也在用 RAGAS，有共同语言 |

### 任务 4：RAGAS 评估的运行方式

**重要差别**——RAGAS v0.3+ 有两种用法：

**方式 A（旧版，不推荐）**：用 RAGAS 内置的 `evaluate()` 函数
```python
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy
results = evaluate(dataset, metrics=[faithfulness, ...])
```

**方式 B（新版，推荐）**：用 RAGAS `SingleTurnSample` + 每个指标的 scorer
```python
from ragas.metrics import Faithfulness, AnswerRelevancy
from ragas import SingleTurnSample

sample = SingleTurnSample(
    user_input="...",
    response="...",
    retrieved_contexts=[...],
    reference="..."
)
score = faithfulness.single_turn_score(sample)
```

本项目用**方式 B**，因为：
- 更灵活——可以对每条样本单独处理
- 可以记录中间结果，方便 Bad Case 分析
- 和后续的 LangSmith Experiment 集成更容易

## 差异化亮点

1. **领域评估集**：30 条手工标注的民航员工 QA 对，面试时可以讲清楚每条的设计意图
2. **分文档类别的指标拆解**：不是只有一个总分，而是看「行李类文档检索精度高不高」「投诉类是否容易生成幻觉」
3. **Bad Case 分类**：检索失败 / 生成幻觉 / 引用错误 → 每类有改进方案
4. **RAGAS SingleTurnSample 模式**：代表你用新版 API，证明你关注技术演进

## 验收标准

- RAGAS 评估流程完整跑通（30 条 QA 对全部评估）
- Faithfulness > 0.70，Answer Relevancy > 0.75
- 评估报告含雷达图 + 按文档类别拆解 + Bad Case 分类
- 30 条手工 QA 对覆盖 7 类文档
