## 二、10 题面试问答

### Q1: 为什么选民航领域做这个项目？

> 民航是典型的高合规、高文件密度行业。一线员工需要掌握数十类政策文档，新员工上手要 3~6 个月。我选择做「内部员工知识助手」而不是「旅客问答机器人」，是因为 E 端项目面试时不需要消费者级 UI 精致度，重点在检索准确性和业务覆盖度。而且内部知识库是每个大企业的刚需，面试官能立刻理解价值。我构建了 7 大类 10+ 份模拟民航政策文档作为知识库素材，证明了领域理解能力。

### Q2: PolicyClauseSplitter 的设计思路？

> 民航政策文档的核心特征是条款编号层级深——"第 3 条 → 第 3.2 条 → 第 3.2.1 条"。通用切片器（如 RecursiveCharacterSplitter）按字符数切，会把"第 3.2 条 托运行李重量限制"切成两半，破坏条款的法律效力。我设计的 PolicyClauseSplitter 用正则识别条款编号模式（`第X条`、`3.2.1`、`（一）（二）`），保证每条条款自成 chunk，子条款保留层级上下文。在 10 份文档上测试，条款完整率 92%，比通用切片器高约 40%。

### Q3: 混合检索为什么比纯向量好？在民航场景有什么优势？

> 民航场景里员工查询分两类：语义型（"行李坏了怎么办"）和精确型（"Y 舱"、"CA1234"、"第 3.2 条"）。纯向量检索对语义型查询效果好，但对"Y 舱"这种缩写无能为力——embedding 模型没见过。BM25 基于关键词匹配，能精确命中。我用 RRF（Reciprocal Rank Fusion）把两个排序列表融合。RRF 公式是 `score(d) = Σ 1/(k+rank_i(d))`，不依赖分数归一化，比加权求和更鲁棒。加上 bge-reranker-v2-m3 重排序，在 30 条测试集上 Precision@5 从纯向量的 0.72 提升到 0.89。

### Q4: 表格你是怎么处理的？

> 民航文档有大量表格——行李限额表、退改签费率表、舱位代码对照表。我用 pdfplumber 做表格感知解析，提取表格为结构化 dict/DataFrame，不做纯文本摊平。切片时把关联表格注入到 chunk 的 metadata 中。检索时除了考文本相似度，还会检查 query 中的数字是否落在表格数值范围内。这样"Y 舱退票手续费多少"能直接命中费率表中的"Y 舱 → 退票 → 5%"。

### Q5: RAGAS Faithfulness 和 Answer Relevancy 的区别？

> Faithfulness 衡量「回答是否忠于检索到的原文」——有没有幻觉。计算方式是把回答拆成原子陈述，逐一检查是否能在原文中找到依据。Answer Relevancy 衡量「回答是否切题」——有没有跑偏。计算方式是逆向生成：给定回答，反问 LLM"这个回答对应什么问题"，再检查原问题和反向生成的问题是否一致。我的系统 Faithfulness 0.82、Relevancy 0.87，说明回答既准确又切题。

### Q6: LangGraph Agent 的状态图设计？

> Agent 有 5 个核心节点：intent_classify（意图分类）、retrieve（检索）、evaluate_confidence（置信度评估）、rewrite_query（Query 改写）、generate（生成回答）。节点间用 ConditionalEdge 实现路由——意图分类后根据 4 种意图走不同路径，置信度评估后根据分数决定是生成、改写还是降级。Self-Reflection 的关键设计点是：改写永远从原始 query 出发，避免「改写漂移」；最多 2 轮；2 轮后仍低置信度就诚实告知而非硬编。

### Q7: 流式输出怎么实现？SSE vs WebSocket？

> 我用 SSE（Server-Sent Events）实现流式输出。后端 generate_stream() 是 async generator，每生成一个 token 就 yield，FastAPI 的 StreamingResponse 逐 token 推到客户端。前端用 `requests.iter_lines()` 消费 SSE 流，逐行解析 `data: token\n\n`。选 SSE 而不是 WebSocket 是因为 RAG 对话是单向推送，SSE 基于 HTTP 更简单——不需要特殊代理配置，Nginx 只需关掉 buffering。

### Q8: 检索不到相关文档时怎么处理？

> 分两层处理。RAG 直连模式：检索无结果时，LLM 的 Prompt 里有安全红线——"如果不确定，必须标注'以下信息可能需要进一步核实'，不要编造"。Agent 路由模式更智能：先用 LLM 改写 Query 换说法重试（Self-Reflection），最多 2 轮。2 轮还不够就进入降级策略——诚实告知用户目前知识库没有相关信息，并给出建议（查原文/换关键词/联系主管）。

### Q9: LangSmith 在你的系统中承担什么角色？

> LangSmith 负责单次请求级别的全链路追踪。每次 RAG 请求在 LangSmith 中形成一棵 Trace 树——embed_query、vector_search、bm25_search、rrf_fusion、rerank、llm_generate 各是一个 Run，嵌套在同一个 Trace 下。我能看到每个环节的耗时和 token 消耗。除此之外我还在系统内建了两层——RAGTraceCallback 做管道节点级计时，ObservabilityCollector 做 P50/P95/P99 聚合趋势监控。三层分别对应调试、性能分析、趋势监控。

### Q10: 这个系统如果上线，最大的风险点和改进方向？

> 最大风险点：① 文档更新滞后——政策变了但知识库没更新，员工拿到旧信息做出错误决策。改进方向是接入文档管理系统的事件通知，政策文档变更时自动触发增量索引。② 答案可靠性——LLM 偶尔会产生看似合理但实际错误的回答（幻觉）。现在已经通过 Prompt 安全红线 + 条款溯源降低风险，但上线前应加上人工反馈机制——员工可以标注"此回答有误"，持续优化。③ 检索精度——民航专业术语的语义理解还有提升空间，可以考虑用民航领域数据做 Embedding 模型微调。

## 三、面试演示流程

### 准备（1 分钟）
1. 启动 `python main.py` + `streamlit run frontend/app.py`
2. 确认知识库已索引（侧边栏文档列表显示 ✅）
3. 准备好浏览器窗口：左侧 Streamlit，右侧 IDE/Swagger

### 演示（5 分钟）

**Step 1: RAG 直连（1 分钟）**
- 输入"旅客行李箱摔坏了怎么赔？"
- 展示流式输出 → 回答中含 `[来源: 托运行李运输规定 第3.2条]`
- 点击引用弹窗，展示原文片段

**Step 2: Agent 路由（1.5 分钟）**
- 勾选 Agent 路由，发同一个问题
- 展示决策面板：意图=政策查询、置信度>80%、改写次数=0
- 发模糊查询"箱子摔烂了怎么办？"
- 展示 Self-Reflection：置信度低 → 改写 → 重新检索

**Step 3: 降级兜底（0.5 分钟）**
- 发非业务问题"今天天气怎么样？"
- 展示 Agent 降级：意图=uncertain → 告知非业务范围

**Step 4: 可观测性（1 分钟）**
- 打开 http://localhost:8000/docs → 调 GET /metrics
- 展示 P50/P95/P99、请求数、错误率

**Step 5: 代码亮点（1 分钟）**
- 打开 IDE 展示 PolicyClauseSplitter 的正则匹配逻辑
- 打开 LangSmith 展示一次请求的完整 Trace 树
