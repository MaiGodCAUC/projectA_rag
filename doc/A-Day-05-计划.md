# A-Day 5：混合检索 + RRF 融合 + 重排序

## 核心目标

实现向量检索 + BM25 关键词检索 + RRF 融合 + 重排序的完整检索链路，用对比实验证明混合检索优于纯向量检索。

## 向量检索核心概念

### 什么是向量检索

向量检索（Vector Search / Dense Retrieval）是 RAG 系统的核心检索方式。它的基本思想是：

```
文本 → Embedding 模型 → 高维向量 → 计算向量间距离 → 距离近 = 语义相近
```

**和传统关键词检索（如 Elasticsearch）的本质区别：**

| 维度 | 关键词检索（稀疏） | 向量检索（稠密） |
|------|------------------|-----------------|
| 匹配方式 | 精确字符串匹配 | 语义向量距离 |
| 同义词 | ❌ "逾重行李"≠"超重行李" | ✅ 向量距离近 |
| 专有名词 | ✅ "CA1234"直接命中 | ❌ 可能被语义相近文本干扰 |
| 跨语言 | ❌ 需要翻译 | ✅ 多语言模型支持 |
| 索引结构 | 倒排索引（Inverted Index） | 向量索引（HNSW/IVF） |
| 存储开销 | 小（词表+倒排列表） | 大（1024维 × N条 × 4字节） |
| 检索速度 | ms 级 | 10-100ms（依赖近似索引） |

### Embedding 向量化的本质

```
文本 "经济舱免费行李额20kg"
  ↓ Embedding 模型（如 BGE-large-zh-v1.5）
  ↓ Transformer 编码器 (24层, 1024维)
  ↓ [CLS] pooling + L2 归一化
  ↓
向量 [0.023, -0.451, 0.712, ..., 0.034]  ← 1024 个浮点数
```

这 1024 个数字「编码」了文本的语义信息——不是人可读的，但数学上可计算：
- 两个向量夹角越小（余弦相似度越接近 1）→ 语义越相近
- 两个向量夹角越大（余弦相似度越接近 -1）→ 语义越相反

### 余弦相似度

```
                query ●
                     /
                    /
        θ 越小    /
        → 越相似  /
                /
               ● document
```

公式：`cosine(A, B) = A·B / (|A| × |B|)`

L2 归一化后简化为：`cosine(A, B) = A·B`（向量内积）

这就是 Qdrant 检索时 `Distance.COSINE` 的数学原理。

### 向量索引 —— ANN 近似最近邻

精确计算 query 和所有 document 的余弦相似度是 O(N × D)，百万级文档不可行。

**ANN（Approximate Nearest Neighbor）算法**用「近似」换「速度」：

| 算法 | 原理 | Qdrant 支持 | 特点 |
|------|------|-----------|------|
| HNSW | 分层可导航小世界图，每层 skip list + 邻居图 | ✅ 默认 | 精度高，内存占用大 |
| IVF | 先聚类（K-means），检索时只搜最近几个簇 | ✅ | 内存省，精度略低 |
| PQ | 向量量化压缩，将高维向量切成子段分别编码 | ✅ | 内存极省，精度再低一档 |

**面试回答**：「Qdrant 默认使用 HNSW 索引，它在精度和速度之间取得了最优平衡。对于十万级文档的民航知识库，HNSW 检索延迟通常 < 20ms。」

## 主流检索方案全景图

```
                          RAG 检索体系
                               │
          ┌────────────────────┼────────────────────┐
          ↓                    ↓                    ↓
      稀疏检索              稠密检索              混合检索
   (Sparse Retrieval)   (Dense Retrieval)    (Hybrid Retrieval)
          │                    │                    │
    ┌─────┴─────┐        ┌─────┴─────┐        ┌─────┴─────┐
    │            │        │            │        │            │
  BM25       TF-IDF    Bi-Encoder  ColBERT    RRF      加权融合
  (本项目)              (向量检索)   (延迟交互)  (本项目)
```

### 方案 1：稀疏检索（关键词匹配）

**代表**：BM25、TF-IDF

**原理**：将文档和查询都表示为「词袋」（Bag of Words），通过词频和逆文档频率计算相关性。

**优势**：
- 精确匹配强：查"第12条"一定命中第12条
- 索引小：只需词表 + 倒排列表
- 速度快：倒排索引 O(查询词数量)

**劣势**：
- 不懂同义词："逾重行李"搜不到"超重行李费"
- 词序无关："北京到上海"和"上海到北京"分数相同
- OOV（未登录词）无法处理

### 方案 2：稠密检索（向量语义）

**代表**：BGE / M3E / OpenAI Embeddings + Qdrant / Milvus / Pinecone

**原理**：将文本编码为固定长度的稠密向量，通过向量距离度量语义相似度。

**流程**：
```
离线建库: 文档 → Embedding → 向量 → 写入 Qdrant
在线检索: Query → Embedding → Qdrant.search(query_vector) → Top-K
```

**优势**：
- 语义理解：能匹配同义词和近义表达
- 跨语言：多语言模型可直接检索
- 无需分词：避免了分词错误的影响

**劣势**：
- 精确查询可能漂移：查"CA1234"可能返回其他航班相关内容
- 存储开销大：1024 维 × 4字节 × N 条
- 依赖 Embedding 质量：模型不行检索就崩

### 方案 3：混合检索（本项目采用）

**核心思想**：稀疏 + 稠密互补，各取所长。

```
Query "CA1234 退票费率"
     │
     ├─→ 向量检索 (BGE)   → 语义相关文档（退票/改签/费率类）
     │
     └─→ BM25 检索 (jieba) → CA1234 精确匹配的文档
              │
              ↓
         RRF 融合
     score = Σ 1/(k + rank)
              │
              ↓
        混合排序结果
              │
              ↓
      Cross-Encoder 重排序 (bge-reranker-v2-m3)
              │
              ↓
         最终 Top-5
```

**为什么 RRF 而不是分数归一化？**

两个检索器的分数不可比：BM25 分数范围 [0, +∞)，向量分数范围 [-1, 1]。直接加权会让 BM25 主导。

RRF 只关注排名，不关注分数绝对值：`score(doc) = 1/(k+rank_vector) + 1/(k+rank_bm25)`

k=60 是经验最优值——既不过于敏感（k 太小，第 1 名和第 2 名差距过大），也不过于平滑（k 太大，排名差异被抹平）。

### 方案 4：Cross-Encoder 重排序

**和 Bi-Encoder 的本质区别**：

| | Bi-Encoder | Cross-Encoder |
|------|-----------|--------------|
| 编码方式 | query 和 doc 分别编码 | query + doc 拼接后联合编码 |
| 速度 | 快（doc 可离线预编码） | 慢（每对都要重新编码） |
| 交互 | 无交互（向量距离） | 全交互（Attention 跨 query-doc） |
| 精度 | 中等 | 高 |
| 使用场景 | 粗排（百万→百） | 精排（百→十） |

**面试回答**：「Bi-Encoder 把 query 和 doc 分开编码后算距离，快但丢失了词级交互；Cross-Encoder 把两者拼接后一起过 Transformer，精度高但慢。我用 Bi-Encoder 粗排取 Top-20，Cross-Encoder 精排取 Top-5，balance 了速度和精度。」

### 方案 5：ColBERT（延迟交互）—— 前沿方案

**原理**：介于 Bi-Encoder 和 Cross-Encoder 之间。doc 的每个 token 都生成一个向量（多向量表示），检索时 query 的每个 token 和 doc 的每个 token 做 MaxSim 匹配。

**优势**：比 Bi-Encoder 精度高，比 Cross-Encoder 速度快  
**劣势**：存储量大（每个 doc 存 N 个向量而非 1 个）  
**本项目暂不采用**：民航文档量不大，Bi-Encoder + Cross-Encoder 足够

### 各方案适用场景总结

| 场景 | 推荐方案 | 理由 |
|------|---------|------|
| 文档量 < 1万，精度优先 | 混合检索 + Cross-Encoder | 延迟可控，精度最高 |
| 文档量 1万~100万 | 混合检索（无 reranker） | 平衡速度和精度 |
| 文档量 > 100万 | 向量检索 + ANN 索引 | 稀疏检索倒排索引过大 |
| 精确匹配为主（法规条文） | BM25 + 向量检索 | BM25 优先级更高 |
| 多语言场景 | 多语言 Embedding + 向量检索 | 跨语言语义匹配 |

本项目（民航内部知识库）属于第一行：文档量小，精度优先，因此采用混合检索 + Cross-Encoder 重排序。

## 代码任务

### 1. `rag/bm25.py` —— BM25 关键词检索引擎

- 基于 rank_bm25 库（BM25Okapi 实现）
- jieba 中文分词
- 增量索引（add/remove documents）
- 统一接口：search(query, top_k) → list[(doc_id, score)]

### 2. `rag/hybrid_search.py` —— 混合检索 + RRF 融合

- 同时调用向量检索 + BM25 检索
- RRF 融合算法：`score = sum(1/(k + rank_i))`
- k 值可配置，支持网格搜索调优
- 返回融合后的结果列表

### 3. `rag/reranker.py` —— 重排序模块

- Cross-Encoder 重排序（bge-reranker-v2-m3）
- 对 Top-N 候选结果精排
- 输出精排后结果

## 差异化亮点

- **混合检索**：向量语义 + BM25 精确匹配互补
- **RRF 融合**：不需要归一化分数的排序融合方法
- **检索对比实验**：4 种策略 × 30 条 query 的 Precision@5 / MRR
- **民航关键词优势**：BM25 对"CA1234""第3.2条"等精确匹配查询天然优于向量
